# Local Excel Intelligent Business Matching MVP Design

## Goal

Build a Python MVP that runs on a MacBook Pro and reads arbitrary Excel workbooks, detects headers, profiles fields, matches Excel columns to standard business fields, supports human confirmation, and learns templates for later reuse.

The MVP scope is the full `milestone_1.md` goal:

- Excel parsing for `.xlsx`, multiple sheets, merged cells, empty rows, and hidden columns.
- Header detection with at least 80% accuracy on generated validation samples.
- Column profiling with `TEXT`, `NUMBER`, `DATE`, and `BOOLEAN` detection.
- SQLite-backed standard field dictionary, aliases, user confirmations, and learned templates.
- Matching through exact, dictionary, RapidFuzz, Embedding/FAISS, and LLM semantic scoring.
- Streamlit as the main user entry point.
- FastAPI as an optional service interface.
- At least 20 generated Excel templates for functional and accuracy validation.
- `pytest` as the required verification command.

## Decisions Confirmed

- The milestone will be implemented as a complete MVP, not a reduced slice.
- The system may download Python dependencies and `BAAI/bge-small-zh-v1.5` during initial setup or first run. After that, embedding inference should use local cache.
- The validation Excel files will be generated by the system.
- The MVP includes built-in standard fields and aliases for four domains: order, CRM, inventory, and finance.
- Streamlit is the primary product interface. FastAPI is a backend or automation interface.
- `codex exec` may use cloud LLM capability for semantic scoring. This is an explicit exception to the local-only constraint in `milestone_1.md`.

## Architecture

Use a layered architecture:

- `excel_matcher/excel/`: workbook parsing, sheet modeling, header detection, and column profiling.
- `excel_matcher/matcher/`: exact, dictionary, RapidFuzz, embedding, LLM, and fusion matching.
- `excel_matcher/vector/`: FAISS index build, persistence, load, and TopK search.
- `excel_matcher/storage/`: SQLite schema and repositories for standard fields, aliases, confirmations, and templates.
- `excel_matcher/services/`: orchestration functions for workbook analysis, field matching, template reuse, and template save.
- `excel_matcher/ui/`: Streamlit app.
- `excel_matcher/api/`: FastAPI app and request/response models.
- `tests/fixtures/`: generated Excel samples and expected outputs.

All business behavior must live in core modules or services. Streamlit and FastAPI should stay thin and call the same service layer.

## Data Models

Use Pydantic v2 models for service and API data contracts. Internal helper objects may use dataclasses only when they do not cross module boundaries.

Core models:

- `WorkbookData`: workbook-level object containing `SheetData` objects.
- `SheetData`: sheet name, dimensions, hidden columns, merged ranges, and cell matrix.
- `CellData`: row index, column index, coordinate, raw value, display value, merged-cell metadata, and source style hints where useful.
- `HeaderDetectionResult`: title row, header row, data start row, confidence, and evidence.
- `ColumnProfile`: column name, column index, inferred data type, null rate, unique rate, sample values, and evidence.
- `StandardField`: field key, Chinese display name, domain, description, and aliases.
- `FieldMatchCandidate`: target field, strategy source, score, and explanation.
- `StageResult`: stage name, status, skip reason if any, candidates, and diagnostic details. Status values are `completed`, `skipped`, and `failed`.
- `FieldMappingResult`: Excel field, target field, confidence, candidate list, per-stage results, and `needs_review`.
- `TemplateSignature`: sheet and structure fingerprint used to reuse confirmed mappings.

## Excel Parsing

Use `openpyxl` as the primary parser because it preserves workbook structure that pandas can lose.

The parser must capture:

- Sheet names and dimensions.
- Cell raw values and display-oriented values.
- Merged cell ranges and each merged cell's anchor.
- Empty rows.
- Hidden columns.
- Multiple sheets.

`pandas` may be used only as an optional helper for tabular analysis after structural parsing is complete.

## Header Detection

Header detection uses heuristic scoring rather than a single "first non-empty row" rule.

Signals:

- Non-empty cell ratio.
- Text cell ratio.
- Whether the next rows look like data rows.
- Presence of business field words such as customer, order, amount, date, quantity, product, account, and inventory terms in Chinese and English where useful.
- Whether rows above look like title rows.
- Merged cells that look like workbook or section titles.
- Hidden columns excluded from main scoring while still preserved in the parsed model.

Output per sheet:

- `header_row`.
- `data_start_row`.
- Optional `title_row`.
- Confidence.
- Evidence explaining the selected rows.

Validation target: at least 80% sample-level accuracy on the generated 20-template set.

## Column Profiling

Field profiles are generated from the detected header row and data region.

Rules:

- Column names come from the header row.
- Empty or merged headers may be filled from nearby header context when the evidence is clear.
- Supported data types: `TEXT`, `NUMBER`, `DATE`, and `BOOLEAN`.
- Date detection supports Excel dates and common string dates.
- Boolean detection supports boolean values and strings such as `是/否`, `Y/N`, `true/false`.
- Profile statistics include null rate, unique rate, and representative samples.
- Profile samples should be available to matching and LLM semantic scoring.

## Standard Dictionary

SQLite is the source of truth for standard fields and aliases.

The built-in dictionary covers:

- Order fields.
- CRM fields.
- Inventory fields.
- Finance fields.

Each field stores:

- Canonical field key.
- Chinese display name.
- Business domain.
- Description.
- Aliases.

The dictionary must support later maintenance through repository functions and API/UI views.

## Matching Pipeline

The scoring path is fixed:

```text
Exact -> Dictionary -> RapidFuzz -> Embedding/FAISS -> LLM
```

Each stage returns a `StageResult`:

```json
{
  "stage": "embedding",
  "status": "skipped",
  "reason": "BAAI/bge-small-zh-v1.5 model is not available",
  "candidates": []
}
```

Rules:

- Execute stages in the fixed order.
- If a stage is unavailable, skip only that stage and continue.
- If a stage is available but raises an unexpected runtime error, mark it `failed`, include the error summary, and continue unless the failure corrupts shared process state.
- The skip reason must be included in API responses and visible in Streamlit.
- Exact and dictionary hits can produce high confidence but should still preserve later stage status diagnostics.
- Final confidence must be based only on successful stages. Do not fabricate scores for skipped stages.
- Mark `needs_review=true` when confidence is below the configured threshold or when the top candidates are too close.

Stage responsibilities:

- Exact matching checks field keys, display names, and aliases after normalization.
- Dictionary matching uses SQLite aliases and confirmed mappings.
- RapidFuzz handles near matches, suffixes, prefixes, punctuation, and minor naming differences.
- Embedding/FAISS embeds Excel fields and dictionary entries using `BAAI/bge-small-zh-v1.5`, then retrieves TopK semantic candidates.
- LLM semantic scoring reranks candidates after Embedding/FAISS by calling `codex exec`.

## Embedding And FAISS

Use `sentence-transformers` with `BAAI/bge-small-zh-v1.5`.

The FAISS index stores vectors for:

- Field keys.
- Chinese display names.
- Descriptions.
- Aliases.

Each vector record keeps metadata:

- `field_key`.
- `alias` or source text.
- `domain`.
- `source_type`.

SQLite remains the source of truth. FAISS is a rebuildable local cache.

Default local paths:

- SQLite database: `data/excel_matcher.db`.
- FAISS index: `data/faiss/index.faiss`.
- FAISS metadata: `data/faiss/metadata.json`.

Index behavior:

- Build on first startup when absent.
- Rebuild after dictionary changes.
- Persist locally, for example under `data/faiss/`.
- Provide TopK query to the matcher.
- If model loading or index access fails, skip the Embedding/FAISS stage and record the reason.

## LLM Semantic Scoring

After Embedding/FAISS returns TopK candidates, an optional LLM scoring stage calls `codex exec`.

This stage is a confirmed exception to the local-only constraint. It may use cloud LLM capability through the user's Codex configuration.

Input:

- Excel field name.
- Column profile samples and inferred data type.
- TopK target candidates.
- Candidate aliases, descriptions, and domains.

Output must be structured JSON:

```json
{
  "target_field": "customer_name",
  "semantic_score": 0.96,
  "reason": "购买方在订单或财务语境下通常表示客户或付款企业"
}
```

Rules:

- The stage is configurable.
- Default timeout is 60 seconds per field. If `codex exec` is unavailable, returns invalid JSON, times out, or has no candidate input, skip the stage and record the reason.
- LLM scoring is a rerank signal, not an unconditional override of strong exact or dictionary matches.
- API and UI must show that this stage may depend on cloud capability.
- Validation reports should distinguish base local-path accuracy from LLM-enhanced accuracy.

## Fusion

The fusion engine merges candidates from all successful stages.

Guidelines:

- Exact and dictionary matches have highest priority.
- RapidFuzz scores are normalized to 0.0-1.0.
- Embedding similarity is normalized and used for semantic recall and ranking support.
- LLM semantic score reranks TopK semantic candidates.
- When highest confidence is below a threshold, default `0.75`, require human review.
- When the top two candidates are close, default difference below `0.08`, require human review.
- Preserve explanations and candidate provenance for UI display and test assertions.

## Template Learning

User-confirmed mappings are saved as reusable templates.

`TemplateSignature` should use:

- Normalized header field sequence.
- Field count.
- Normalized field name set.
- Column order similarity.
- Data type distribution.
- Sheet name as a weak feature only.

Reuse behavior:

- High-similarity templates can directly provide mappings.
- Medium-similarity templates should be shown as recommendations that need review.
- Low-similarity workbooks use the full matching pipeline.

Saved template data:

- Workbook or sheet signature.
- Confirmed `excel_field -> target_field` mappings.
- Domain when known.
- Creation and update timestamps.

## Streamlit UI

Streamlit is the main user interface.

Flow:

1. Upload Excel.
2. Display workbook and sheet summary.
3. Display detected title/header/data-start rows.
4. Allow manual adjustment of header row and data start row.
5. Display column profiles.
6. Display mapping results, confidence, candidate list, and `needs_review`.
7. Display every scoring stage status: Exact, Dictionary, RapidFuzz, Embedding/FAISS, and LLM.
8. Display skip reasons for unavailable stages.
9. Allow the user to change mappings.
10. Save confirmed mappings as a template.
11. On later uploads, show template reuse results when a structure matches.

The UI should stay thin and call service functions.

## FastAPI

FastAPI exposes optional automation endpoints over the same service layer.

Endpoints:

- `GET /health`: component availability for SQLite, FAISS, embedding model, and LLM scorer.
- `GET /fields`: standard fields and aliases.
- `POST /workbooks/analyze`: upload Excel and return workbook structure, header detection, and column profiles.
- `POST /fields/match`: match supplied field profiles and return mapping results with stage diagnostics.
- `POST /templates`: save confirmed mappings as a reusable template.

API responses must include stage status and skip reasons.

## Generated Validation Samples

The project will generate at least 20 Excel samples covering:

- Order templates.
- CRM templates.
- Inventory templates.
- Finance templates.
- Multiple sheets.
- Merged title cells.
- Header rows offset by title or blank rows.
- Empty rows.
- Hidden columns.
- Different column orders.
- Alias-heavy field names.
- Ambiguous fields that require review.

Generated samples must include expected header rows, data start rows, and expected field mappings for accuracy checks.

## Testing And Verification

The required verification command is:

```bash
pytest
```

Test areas:

- Excel parsing.
- Header detection.
- Column profiling.
- SQLite repositories.
- Built-in dictionary seeding.
- RapidFuzz matching.
- Embedding/FAISS behavior when available.
- Stage skipping when Embedding/FAISS or LLM is unavailable.
- Fusion confidence and `needs_review`.
- Template signature matching and reuse.
- Generated sample accuracy.
- FastAPI service behavior through test client where useful.

Accuracy reporting:

- Header detection accuracy must be at least 80%.
- Field matching accuracy must be at least 85%.
- Base matching accuracy and LLM-enhanced matching accuracy should be reported separately.
- Required automated acceptance uses deterministic generated samples. If the cloud LLM stage is unavailable during tests, tests must verify the skip behavior and report base accuracy.

Streamlit should avoid fragile browser-level assertions. Its business behavior should be covered through the shared service layer.

## Non-Goals

- No cloud vector database.
- No Milvus, Qdrant, or Weaviate.
- No OpenAI, Claude, Gemini, or other cloud APIs except the explicitly approved `codex exec` LLM semantic scoring stage.
- No production authentication or multi-user permissions in this MVP.
- No `.xls` support unless added later; this milestone requires `.xlsx`.

## Completion Criteria

The MVP is complete when:

- Excel parsing is implemented.
- Header detection is implemented.
- Column profiling is implemented.
- RapidFuzz matching is implemented.
- Embedding matching is implemented.
- FAISS retrieval is implemented.
- LLM semantic scoring through `codex exec` is implemented as a configurable stage.
- Streamlit UI is implemented.
- SQLite dictionary and template learning are implemented.
- Stage skipping and skip reasons are visible in UI/API.
- At least 20 validation Excel files are generated and tested.
- `pytest` passes.
- Header detection and field matching accuracy targets are met.
